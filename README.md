# Умный кредитный кабинет предпринимателя

Full-stack прототип сквозного кредитного процесса для малого и микробизнеса: от определения потребности и автоматического подбора продукта до решения сотрудника банка, документов и моделируемой выдачи.

## Ценность решения

**Для предпринимателя:** понятный путь без необходимости разбираться в банковской продуктовой линейке. Клиент указывает цель, точную сумму и срок, получает предварительный расчёт, подаёт предзаполненную заявку и всегда видит текущий этап и следующий шаг.

**Проблемы банка:** ручной сбор разрозненных данных, повторная проверка заявок и перенос информации между этапами замедляют решение. Кабинет объединяет досье, проверку полноты, синтетические сведения БКИ и ЕГРЮЛ/ЕГРИП, объяснимую оценку риска и очередь решений. Продуктовая гипотеза — сократить ручную подготовку и число поздних отказов; количественный эффект в демо не измерялся.

## Гипотезы и KPI пилота

Демо не доказывает экономический эффект. Для пилота до запуска фиксируется исходный уровень, затем на сопоставимых сегментах сравниваются медиана и `p90`; очередь уже показывает объём работы, возраст заявки и SLA.

| Гипотеза | KPI и формула | Что должно подтвердить ценность |
|---|---|---|
| Единое досье ускоряет решение | `TAT = decided_at − submitted_at`, медиана и `p90` | Снижение времени до решения без роста доли ошибок |
| Проверка полноты сокращает возвраты | `MORE_INFO / SUBMITTED` и среднее число циклов уточнения | Меньше заявок и повторных запросов, требующих данных |
| Подбор продукта снижает поздние отказы | `OFFER / SUBMITTED`, отдельно по причине отказа | Рост конверсии в предложение при стабильном риск-профиле |
| Прозрачный оффер улучшает завершение пути | `ISSUED / OFFER` и время `OFFER → READY_FOR_ISSUANCE` | Меньше незавершённых офферов и быстрее ознакомление |
| Приоритизация разгружает аналитика | Число заявок «требует действия», доля старше `24/48 ч` | Снижение просроченной очереди и ручного поиска |
| Автоматизация убирает лишние операции | Число ручных точек принятия решения и действий на заявку | Решение сотрудника остаётся обязательным, технических действий становится меньше |

Целевые значения задаются только после измерения baseline на реальном процессе; неподтверждённая экономия в материалах не заявляется.

## Что реализовано

| Область | Реализация |
|---|---|
| Подбор кредита | Система фильтрует продукты по цели, выручке, сумме и сроку; каждая рекомендация и альтернатива содержит серверный расчёт ставки, платежа, переплаты, общей выплаты и индекса соответствия |
| Предварительный расчёт | Индекс соответствия правилам (не вероятность одобрения), ставка, аннуитетный платёж, общая выплата, переплата и кредитный потенциал; визуально отмечено, что это не оферта и не решение банка |
| Заявка | Создаётся из неизменяемого снимка расчёта; продукт, сумма, срок и категория цели заблокированы от случайного изменения |
| Клиентский путь | Понятный timeline, следующий шаг, типизированный запрос дополнительных сведений и восстановление после сетевых ошибок |
| Банковский путь | Очередь с поиском, сортировкой, фильтром действий, счётчиками и SLA; единое досье, проверка отчётности, внутренний rule-based скоринг и решение сотрудника |
| Результаты | Подтверждение условий, изменение условий, запрос сведений или отказ с понятным объяснением |
| Экономика оффера | Сервер сохраняет сумму, ставку, срок, платёж, переплату, общую выплату, тип платежа и срок действия предложения |
| Документы и выдача | Предпросмотр и контролируемое скачивание трёх демонстрационных документов с автоматическим обновлением прогресса, подтверждение ознакомления, отдельные этапы подписания и выдачи |
| Профиль | Данные пользователя и компании, финансовые показатели, проверяемые demo-направления поддержки с локальным checklist и осторожный совет по рефинансированию |
| Надёжность | RBAC, idempotency критических команд, reconciliation неизвестного результата, confirmation dialogs и Error Boundary |
| Проверяемость | OpenAPI 3.1, unit/integration, HTTP/RBAC, browser E2E и axe accessibility smoke |

## Важные границы демо

- Все пользователи, компании, финансовые показатели, кредитные истории, новости, заявки и документы синтетические.
- Продукты, ставки и лимиты — демонстрационные допущения, а не действующая линейка или публичная оферта Альфа-Банка.
- БКИ и ЕГРЮЛ/ЕГРИП представлены локальными provider-моками; внешние сервисы не вызываются.
- Скоринг и подбор детерминированы и объяснимы, но не являются валидированной банковской ML-моделью.
- Помощник и саммари работают только по шаблонам с маркировкой «без ИИ»; модель, API-ключ или отдельный AI-runtime не требуются.
- Направления поддержки — идеи для последующей проверки, а не подтверждение права на льготу.
- Совет по рефинансированию не выдумывает новый платёж или экономию: он сообщает, какие данные нужны для отдельного сравнения.
- Подписание и выдача моделируются. Прототип не создаёт квалифицированную ЭП, банковскую проводку и движение денег.

## Архитектура и конфигурация

React SPA и Hono API собираются в один Node.js-контейнер. Сервер выполняет бизнес-проверки и хранит заявки, snapshots, документы и аудит в SQLite; база вынесена в именованный Docker-том. Подробные компонентная схема, state diagram, модель данных и production-граница приведены в [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `PORT` | `3000` | HTTP-порт приложения при запуске собранного сервера |
| `DATA_DIR` | `./data`; в Compose — `/app/data` | Каталог SQLite и демонстрационных документов |
| `COOKIE_SECURE` | `false` | Установить `true` при публикации только через HTTPS |

Для стандартной проверки дополнительные `.env`-настройки не нужны.

## Требования к компьютеру

Решение рассчитано на стандартный офисный компьютер:

- `8 ГБ` оперативной памяти достаточно для демонстрационного запуска, `16 ГБ` рекомендуется для параллельной сборки и тестов;
- дискретная видеокарта не требуется;
- локальная AI/LLM-модель не используется и не загружается;
- требуется Docker Desktop либо Docker Engine с Compose plugin;
- после первого получения Docker-образа и npm-зависимостей основной сценарий не обращается к внешним API.

## Быстрый запуск для проверки

Из корня проекта:

```bash
docker compose up --build
```

После запуска откройте:

- приложение — <http://localhost:3000>;
- интерактивную документацию API — <http://localhost:3000/api/docs>;
- OpenAPI 3.1 — <http://localhost:3000/openapi.json>;
- health check — <http://localhost:3000/api/health>.

Остановка без удаления данных:

```bash
docker compose down
```

SQLite хранится в именованном томе `appdata`. Не используйте `docker compose down -v`, если нужно сохранить созданные заявки.

## Сценарий для демонстрации жюри

> Создавайте новый расчёт и новую заявку. Запишите её публичный номер `АБ-...` и используйте его при переключении между ролями.

1. Войдите как `client1` и откройте калькулятор.
2. Укажите цель «оборотные средства», сумму `1 500 000 ₽` и срок `12 месяцев`.
3. Сравните рекомендованный продукт и альтернативы: в каждой карточке должны быть индекс соответствия без знака `%`, ориентир ставки, платёж, переплата и общая выплата. Кнопка перехода к заявке находится после экономики варианта.
4. Выберите рекомендацию либо подходящую альтернативу и перейдите к заявке: сервер создаст отдельный снимок выбранного варианта, а его параметры будут предзаполнены и заблокированы. Добавьте описание цели и подтвердите отправку.
5. Откройте созданную заявку, запишите публичный номер и убедитесь, что автоматический путь завершился на этапе «Рассмотрение сотрудником», а не автоодобрением.
6. В отдельном профиле браузера либо после выхода войдите как `bank`. Найдите заявку по публичному номеру, изучите досье и подтвердите предложенное решение.
7. Вернитесь под `client1`. Сравните запрошенные и предложенные условия, полную экономику и срок действия оффера. Подтвердите принятие.
8. Просмотрите один документ прямо в карточке, затем скачайте договор, график и справку. Прогресс должен обновляться автоматически; после ознакомления подтвердите пакет и выполните только моделируемое клиентское подписание.
9. Под `bank` найдите ту же заявку в фильтре «Ожидает подтверждения выдачи» и отдельно подтвердите моделируемую выдачу.
10. Под `client1` проверьте итоговый экран `ISSUED`: времена подписания и банковского подтверждения, итоговую экономику и подписанные документы.

Альтернативные и негативные ветки описаны в [`docs/TEST_SCENARIOS.md`](docs/TEST_SCENARIOS.md).

## Проверки качества

```bash
npm run check
npm run test:e2e
```

Проверенное состояние проекта:

- `105/105` unit/integration-тестов;
- `12` HTTP/RBAC-сценариев внутри test suite;
- `5/5` Playwright-тестов: выбор альтернативы, основной путь, ветки решений и два axe smoke;
- OpenAPI contract test для всех `32` операций;
- `npm audit --omit=dev` — `0` известных уязвимостей.

`npm run test:e2e` использует отдельный Compose project `alfa-e2e`, порт `3100` и каталог `.tmp/e2e-data`; основной том `appdata` не затрагивается.
